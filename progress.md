- 2026-10-30, `t3/daemon-modes` (code and cargo tests only). **One daemon per CEF mode, started when a render needs it.** Raster mode and software WebGL are fixed for a running CEF, so the socket (Windows: the port file) is keyed by both: `vrf-daemon-<uid>.sock` for CPU raster, `-fast` for GPU raster, `-swiftshader` for SwiftShader WebGL, `-fast-swiftshader` for both (`daemon::socket_for`; `VRF_SOCKET` gets the same suffixes). The client picks the socket of its own mode (Remotion `reference`, HyperFrames `fast`, `--mode` overrides). When that socket has no daemon but another mode's does, `vrf render` starts `vrf daemon --mode <its mode>` detached beside it (`daemon::spawn_detached`), says so in one line, waits for it, and renders there; later renders of that mode are warm. With no daemon of any mode it renders in process as before, so nobody gets a daemon they did not ask for. A plan must be cached first (otherwise the render is in process and fills the cache, as before). `vrf daemon --stop` stops every mode's daemon. Windows: `spawn_detached` clears the inherit flag on the client's std handles first, because a Windows child inherits the caller's pipes and `vrf render | …` (or `Command::output`) would wait until the daemon exited; found as a hang of the new cli test on win-pc. - 2026-10-30, `t3/windows-video` (code and cargo tests only, from `t3/engine-tip` `871d76e`). **Native video on Windows.** The shared-memory protocol, `Link`, `Stream`, `js/video.js` and `js/hyperframes-hop.js` are unchanged; only the decoder behind `Clip`/`Reader`/`Frame` is new (`video/decoder_win.rs`, Media Foundation). Frame times come from our own container reader, `video/mp4.rs` (platform-neutral, public): stts, ctts, stss and the edit list mapped the way `decode.m` maps AVFoundation's segments (empty edits shift, samples outside every segment are dropped, sort by movie time), so the table, the keyframes and the frame ids are the macOS ones. On macOS the test `the_container_table_is_the_decoders_and_ffprobes` shows the reader equals AVFoundation's table, and on both OSes it equals ffprobe's. Decoding: `IMFSourceReader` with the video stream only, NV12 requested, DXVA through a D3D11 device manager (`MF_SOURCE_READER_D3D_MANAGER`, texture copied to a staging texture and read back), software MFT when there is no device or the decoder returns memory (`MF_SOURCE_READER_DISABLE_DXVA`); `Reader::open` starts at the keyframe at or before `from` and skips frames before it, as on macOS. Media Foundation's sample times follow the container except that it ignores an empty edit (`off1080.mp4`), so `Clip::open` decodes the first frame and finds the offset between its time and the table (0, minus the empty edit, or media minus movie time); a clip whose first timestamp matches none, whose decoded size differs from the container's, or whose edit list has several segments is refused and goes to the framework's own extraction. Matrix and range: `colr` first (unspecified matrix counts as untagged), then the decoder's output type (the stream's VUI), as AVFoundation does from the format description and the pixel buffer. The CLI default is `--video native` on both OSes. `hyperframes-native.mjs` matches `/compiled/` with backslashes turned into slashes.

- Surprise, Windows Remotion's compositor does not convert like the macOS one. Our shader reproduces the macOS compositor's swscale arithmetic (`SWS` table in `video.js`): Y 235, U and V 128 give 253, Y 126 gives 126. On win-pc Remotion's own frame of `cfr1080.mp4` frame 0 has 255 for that white and 128 for that grey, so native against Remotion's frames differs by up to 3 (mean 0.55 to 1.0, 7 to 19% of pixels over 1), uniform over the video, while ffmpeg's default x86 conversion differs from Remotion's by up to 2. So Windows renders carry the macOS pixels (the scoring references are macOS frames) and not the Windows Remotion pixels. `colours_equal_remotions_own_frames` allows 3 on Windows (1 on macOS) and the transform test FLIP 0.02 on Windows (0.01 on macOS): `Rates`, which has no transform, gives FLIP 0.0184 from the colour offset alone, `Two` 0.0170. Deriving the x86 compositor's arithmetic for a second `SWS` table is the way to match Windows Remotion exactly; not done.
- HyperFrames colour against its ffmpeg extraction (`hyperframes_native_video_colours_equal_extraction`, thresholds 0.02 and 0.1%): Windows FLIP mean 0.0141, 0.0149, 0.0184 (`cfr1080-full`), 0.0143 against 0.011 to 0.0125 on macOS; over 32 0.0000%. The extraction runs on x86 ffmpeg there; not isolated further.
- Speed risk, not timed: each reader decodes synchronously (`ReadSample`), one session per view and clip; Media Foundation's rate per reader at 1080p was in the low hundreds of frames per second in a probe, with hardware and software alike, so a render faster than that on one clip could wait on decode (more views each have their own reader). Every `Clip::open` decodes a frame and the first one creates the D3D11 device.
